# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

"Gangetabellen" is a Norwegian-language multiplication-table (and add/subtract/divide) practice app for kids. The app is static: one HTML page per design (`index-classic.html`, `index-minecraft.html`, `index-cat.html`, each with its own stylesheet in `css/`), `index.html` as a tiny router, and `js/*.js` (game logic, plain classic scripts sharing global scope, loaded in order by `<script>` tags at the bottom of each design page). To make a different UI, copy a design page, give it its own stylesheet, register it in `THEMES` in `js/theme.js` and in `scripts/check.sh`, and keep the same ids/classes the JS uses; the game play stays the same. There is no build step, package manager, linter, or test suite.

There are four designs sharing the same `js/` (the fourth, `index-build.html`, is described below): the original (`index-classic.html` + `css/style.css`), a cosy cat theme for older girls (`index-cat.html` + `css/cat.css`: pastel lilac with paw prints, colour-coded operation chips, number bubbles, a cat that walks along the progress bar; original artwork, no Pusheen assets, font Baloo 2), and a blocky game-world theme (`index-minecraft.html` + `css/minecraft.css`: dirt/grass page, inventory-style panels, a hotbar of slots for the operations, an XP-style progress bar; original pixel styling, no game assets). All must keep the ids/classes the JS uses. In the Minecraft page the score panel sits inside the sticky `#progress-container`, and its font is Jersey 10 on purpose (Pixelify Sans reads 5 as S and 7 as mirrored). `scripts/check.sh` runs the scenarios against all three design pages (add new design pages to its `for page in` list).

3D build design (`index-build.html` + `css/minecraft.css` + `css/build.css`, `js/build3d.js`, vendored `js/vendor/three.min.js`): the Blokkverden page plus a three.js stage inside the sticky `#progress-container`. Every correct answer drops blocks onto a random voxel picture (`BUILD_PICTURES`, each ≥100 blocks so a 100-problem test adds ≥1 block per answer; `blocksForProgress` = floor(blocks · solved / problems)). `build3d.js` changes no game code: it wraps `renderScore`/`renderProgress` (loaded after `render.js`/`game.js`) and counts `.answer-input[data-solved="1"]`. Blocks are only ever added during a test; a fresh state (no answers) picks a new picture. Picture, seed and shown count are saved in `localStorage` (`gangetabellen.build`). three.js is pinned to r159, the last release with a classic (non-module) `three.min.js`, so no build step and it works from `file://`; don't upgrade to r160+ (ES modules only). No WebGL: the stage hides and the game still works. `getBuildInfo()` is for the scenarios; `playwright-scenarios/build3d.mjs` runs only on this page. Bump the `?v=` on stylesheet links when you change a stylesheet (tablets cache them).

Design switcher: `js/theme.js` renders `<nav id="theme-switcher">` as links to the design pages (each `<body>` has `data-theme`), saves the pick in `localStorage` (`gangetabellen.theme`) and `index.html` redirects to it before rendering (default classic). The game session is shared between designs, so switching mid-test keeps progress. Each stylesheet styles `.theme-switcher`/`.theme-option` itself.

## Commands

- Run locally: open `index.html` in a browser (it redirects to the design picked last; pick one with the switcher at the top of any page) (works from `file://`; keep scripts as classic `<script src>`, not ES modules, which are blocked on `file://`).
- Checks: run `scripts/check.sh` from anywhere. It syntax-checks every `js/*.js`, then runs every `playwright-scenarios/*.mjs` (currently `gameplay.mjs`, `sticky-progress.mjs`, `persistence.mjs`, `summary.mjs`, `theme-switcher.mjs`, `build3d.mjs`) in headless Chromium via the `verify-webpage` Claude skill (installed in `~/.claude/skills`, not in this repo; it manages Playwright itself, so don't add it to the repo), printing only failures and the tally. New scenario files are picked up automatically. The script wraps `node ~/.claude/skills/verify-webpage/scripts/verify.mjs --root . --test <each scenario> --seed 1`.
  They default to desktop and phone viewports (tablet is not covered). Run them after changing any design page. When you change the page structure (ids, classes, DOM layout) or add/remove/alter functionality, update the scenarios to match (and add new ones for new features) in the same change.
- Deploy: GitHub Pages is set to "Deploy from a branch" (`main`, `/`), so pushing to `main` publishes the repo root as-is. There is no Actions workflow. To republish without a commit: `gh api -X POST repos/oyvindma/gangetabellen/pages/builds`.

## Architecture

- UI text is Norwegian; keep new user-facing strings in Norwegian.
- Fonts (Nunito, Fredoka One) load from Google Fonts; styling uses CSS custom properties (e.g. `--secondary-color`) and has responsive breakpoints for small screens (recent work: 2-column layout, sticky progress bar).
- The JS is split by section into `js/` (`config`, `clock`, `problems`, `layout`, `render`, `game`, `answers`, `controls`, `summary`, `persistence`, `main`; order in the design pages matters). Sections: config constants, a single `state` object, problem model (`buildProblem`, `generateDistributedProblems` — pure data, no markup), layout (`layoutProblems`, `columnFirstOrder`), rendering (`formatEquation`, `setInputState`, `renderScore`, `renderProgress`), game state (`resetGameState`, `awardCorrectAnswer`), answer checking, and controls. Keep markup out of the problem model and DOM writes out of the game-state functions.
- Flow: `window.onload` / any control change → `createMathProblems()` → `readSelections()` (defaults to numbers 1–10 and multiplication, and ticks the boxes) → `generateDistributedProblems()` (`TOTAL_PROBLEMS_COUNT` = 100, spread evenly over operations) → `displayProblems()` → `layoutProblems()` → `setAnswersVisible()` (also resets score/progress).
- Sorted order is column-first: `layoutProblems()` reorders the existing DOM nodes (by `data-rank`) using the grid's *current* column count read from CSS, and re-runs on resize without losing answers. Don't hardcode column counts.
- Whether an input is solved is stored in `input.dataset.solved`, set only via `setInputState()`; points are awarded only on the first correct answer.
- `toggleOrder()` regenerates via `createMathProblems()`; `toggleAnswers()` fills/clears inputs and resets score. The session is persisted in `localStorage` (`STORAGE_KEY`): config, the problem list (`state.problems`), per-input value/state and score, written by `saveSession()` and rebuilt on load by `restoreSession()` (falls back to `createMathProblems()`). Every settings control calls `onConfigChange(el)` and the `#clear-btn` calls `clearTest()`; both ask `confirmDiscardProgress()` (true only if `hasProgress()`, i.e. non-read-only inputs have text) and revert the control if declined. Clear generates a new test. No backend.
- Timing and summary: every timestamp comes from `activeNow()`, an *active clock* that stops while the page is hidden (screen off, tab/app switch, `visibilitychange`/`pagehide`), the window is unfocused (`blur`), or there has been no input for `IDLE_MS` (60 s; `noteActivity()` resumes it), so paused time never counts towards a problem. Each problem's time is capped at `MAX_QUESTION_MS` (30 s). `startQuestionTimer`/`recordQuestionTime` fill `state.questionTimes` (rank → ms, first focus to first answer); `state.incorrect` holds ranks with a wrong answer. When the last problem is answered, `markAnswered()` calls `showSummary()` (modal `#summary-modal`). "Prøv igjen" (`restartTest`) reuses the same problems; "Bli enda bedre! 💪" (`practiceStruggled`) builds a test of the same size from `findStruggledRanks()` (wrong answers plus times above median + 0.5·scaled MAD, which is robust to outliers) via the pure `findSlowRanks`/`buildPracticeSet`. All new tests start through `startTest(problems)`. Timing is saved in `localStorage` under `timing`.
- "Kun store tall" (`#large-numbers-toggle`): `generateDistributedProblems(..., largeNumbersOnly)` keeps only problems where both operands are ≥ `LARGE_NUMBER_MIN` (5). `renderLargeNumbers()` disables/unticks the 1–4 buttons; `readSelections()` never default-ticks disabled boxes. Saved as `config.largeNumbers`.
